# Hosting pryx

Open the service's HTTPS address to find its key location and connect. Enter the key to see
this install's caller examples; the page keeps it only for the current request in this tab.
Examples reference `PRYX_API_KEY`, never its value. Keep your state volume across replacements.
The image exposes only port `8080` (`PORT` overrides it), with readiness at `/healthz`.

These files target release `0.1.0`. Template documentation was checked on 2026-11-14.
They do not create an account or publish a marketplace listing. Template publication, where
needed, remains a maintainer operation. See each platform's own pricing link below.

## Tiers and guarantees

The current main branch predates the [any-host probe and presets](any-host.md#4-the-design).
No platform name proves a kernel capability. The welcome page reports the configured default
isolation, with the absent probe report explicitly stated. Node admission still refuses
unsupported requests. No extra privilege, engine socket, device or host policy override is
added by these templates. The image chooses from what it can use; no preset flag is required.

On an ordinary container, the default process tier requires Landlock and seccomp. It refuses
startup when it cannot enforce that floor. Root gives per-sandbox UIDs; an ordinary service
user gives shared UID isolation, which is weaker and is reported. There are no container
images, browser/desktop templates or memory-preserving sleep in this process path. User
namespaces and writable cgroups are not assumed. See [process tier](process-tier.md).
Wasm is available on x86-64 when explicitly selected at deployment, with a virtual kernel,
shared sidecar and [its limits](agentos.md); it does not substitute for a requested process policy.
Container requires an engine and host firewall, absent on these managed-service templates.
KVM/VM and the new guarantees report depend on the any-host work and are not advertised here.

A provider can change its kernel without changing a template. Only a live probe can establish
Landlock ABI, seccomp, user namespaces and cgroup delegation there; live deployments below
have **not run**. Local Docker constraints in CI are reproducible envelopes, not claims about
a provider kernel. Platform validation and live deployment are separate evidence.

## Render

[Deploy on Render](https://render.com/deploy?repo=https://github.com/cubepals/pryx)
uses the [root Blueprint](../render.yaml), one state disk and managed Postgres.
`PRYX_BOOTSTRAP_API_KEY` is generated by Render; retrieve it in the service's **Environment**
settings. It is neither logged nor sent with the public welcome page. `RENDER_EXTERNAL_URL`
provides the verified HTTPS origin. The image's default user is root; Render supplies the
container filesystem and disk at `/var/lib/pryx`. Host namespaces/cgroups are not assumed.
The ordinary-container process policy above applies; no Docker or KVM is attached.

Validation: Render's own JSON Schema in the existing CI deployment suite; image envelope and
six caller blocks in that same suite. Live deploy: not run.
[Blueprint reference](https://render.com/docs/blueprint-spec),
[persistent disks](https://render.com/docs/disks), [pricing](https://render.com/pricing).

## Railway

[Prepare Railway deployment](../deploy/platforms/railway/template.md).
Templates are account-owned; the file lists every Composer field to paste. A maintainer can
publish those fields and use the returned deploy URL as the button; no template is published
here. Use one instance, one `/var/lib/pryx` volume, generated domain and `/healthz`.
`PRYX_BOOTSTRAP_API_KEY=${{secret(64)}}` is generated in Template Composer; find it in
**service → Variables**. `RAILWAY_PUBLIC_DOMAIN` gives the HTTPS origin. Keep the image's
root user, writable container filesystem and its one state volume. Process admission still
requires the kernel policy above; no user namespace, delegated cgroup, Docker or KVM is assumed.

Validation: no account-free template validator exists for Composer fields. CI tests the
recorded container envelope and caller blocks. Live deploy: not run.
[Templates](https://docs.railway.com/templates),
[variable functions](https://docs.railway.com/variables/reference),
[volumes](https://docs.railway.com/volumes), [pricing](https://railway.com/pricing).

## Fly.io

[Prepare Fly deployment](../deploy/platforms/fly/fly.toml).
Fly Launch assigns a unique app name and attaches `pryx_state` to one machine. Use that file
with Fly Launch; do not scale to a second machine with an independent state volume.
Fly's secrets store accepts supplied values but the launch config does not generate one:
the image prints its initial `apiKey` once in **app → Monitoring → Logs**.
`FLY_APP_NAME` gives the HTTPS origin. Fly runs the image in a Machine with a writable root
filesystem and its persistent `/var/lib/pryx` mount; the image user stays root. This template
adds no Docker daemon or KVM device. The process policy must pass on the actual guest kernel.

Validation: the TOML is parsed locally in CI; Fly's remote configuration validation needs an
app/account and is not reported as run. The container envelope and caller blocks run in CI;
these do not emulate a Fly microVM. Live deploy: not run.
[Configuration](https://fly.io/docs/reference/configuration/),
[volumes](https://fly.io/docs/volumes/overview/), [pricing](https://fly.io/docs/about/pricing/).

## DigitalOcean App Platform

[Use a rented machine](../deploy/platforms/cloud-init/user-data.yaml).
App Platform has no persistent volumes. Three storage paths were checked: managed Postgres
leaves sandbox data ephemeral; Postgres with Spaces still loses local fleet identity; keeping

## Koyeb

[Prepare Koyeb deployment](../deploy/platforms/koyeb/template.md).
The deploy-button format supports an image, variables and ports but not a volume attachment.
A bare button loses state; an external database still loses local identity and sandbox data;
a pre-created volume works but needs account preparation. Prepare that volume and service
using the supplied fields. No account or template is published. Read `apiKey` once in
**service → Logs**; the button format has no documented generated-secret expression.
`KOYEB_PUBLIC_DOMAIN` gives the HTTPS origin. Keep one instance with its `/var/lib/pryx` volume,
port `8080`, writable root filesystem, image default user and no privileged mode. Actual
Landlock/seccomp support must be established by admission; no namespace/cgroup/KVM guarantee
is inferred from Koyeb's isolation technology.

Validation: no account-free service validator is documented. CI exercises the ordinary
container envelope and caller blocks, not Koyeb's kernel. Live deploy: not run.
[Button format](https://www.koyeb.com/docs/build-and-deploy/deploy-to-koyeb-button),
[volumes](https://www.koyeb.com/docs/reference/volumes), [pricing](https://www.koyeb.com/pricing).

## Coolify

[Prepare Coolify deployment](../deploy/platforms/coolify/compose.yaml).
In an existing Coolify installation, add a Docker Compose Empty service and paste the file.
`SERVICE_URL_PRYX_8080` asks Coolify to assign the proxy domain;
`SERVICE_PASSWORD_64_PRYX` generates the bootstrap key. Retrieve it in **service → Configuration
→ Environment Variables**. Keep the named volume, image user, writable container root and
ordinary Docker security policy. Coolify runs on your host: Landlock/seccomp availability
comes from that host, and no engine socket, privilege or KVM device is passed to pryx.
No catalog entry is published. The generated URL uses the Coolify installation's domain/TLS
policy; the operator must already have configured HTTPS there.

Validation: Docker Compose's own config validator with generated values supplied in CI;
container envelope and caller blocks in the same suite. Live deploy: not run.
[Compose](https://coolify.io/docs/services/configuration/docker-compose),
[generated variables](https://coolify.io/docs/services/configuration/environment-variables),
[pricing](https://coolify.io/pricing/).

## A machine of your own

Supply [user-data.yaml](../deploy/platforms/cloud-init/user-data.yaml) as cloud-init user data.
It runs the existing installer and `pryx up --image` once as root, keeping state on the machine's
disk. This is the existing server installation: Docker and its host firewall policy are installed;
the image uses the container tier and refuses a missing policy. It ends at the same welcome
page on port `8080`. The key location is the first successful startup in the service journal.

The unattended server preset and public HTTPS discovery are dependencies of the any-host
installer. On current main the server endpoint is HTTP, and its default origin is loopback:
reach the welcome page through an SSH tunnel. A public HTTPS deployment needs the existing
operator DNS/TLS setup and PRYX_PUBLIC_URL; this file does not invent a domain or weaken TLS.
No cloud-init provider or operating system can allocate a verified domain for a machine from
this repository alone.

Validation: cloud-init's own schema validation and scheduled boot of the file are CI checks;
no boot ran on the supervised development machine. Live deploy: not run.
[cloud-init runcmd](https://docs.cloud-init.io/en/latest/reference/modules.html#runcmd).
